# 计时与休眠

## 已确认规格

工作与休息在系统休眠时采用相反语义：

| 休眠前状态 | 休眠期间 | 唤醒后 |
| --- | --- | --- |
| 用户已手动暂停 | 冻结 | 仍暂停，剩余不变 |
| 工作中 | 冻结 | 从睡前剩余量自动继续 |
| 休息/强制期 | 墙钟继续 | 立即按当前时间补算；到点后允许解锁 |

“合盖”本身不是计时事件。合盖但系统仍因外接屏继续运行时，工作 timer 正常推进；只有 OS 真正发出挂起/睡眠通知才冻结工作。

休息到点不自动关闭遮罩。用户唤醒电脑后会看到休息已完成，并手动点击“解锁并继续工作”。

## 当前 Rust 实现

### 平台通知

- macOS：监听 `NSWorkspaceWillSleepNotification` 与 `NSWorkspaceDidWakeNotification`；
- Windows：专用 message-only HWND 接收 `WM_POWERBROADCAST` 的 suspend/resume 消息。

原生回调发生时立即记录 `Instant` 和 `SystemTime`，再把事件送入通道。主 UI 每秒消费队列时使用事件原始时间戳，而不是消费时刻；即使“将睡眠”和“已唤醒”两条消息都积压到唤醒后，也能把工作冻结在真正的睡前位置。

### 工作冻结

收到 `Suspended` 时：

1. 用通知携带的单调时间同步工作剩余；
2. 清除工作起点并把 `running` 设为 false；
3. 记录 `resume_work_after_suspend=true`。

收到 `Resumed` 时，从冻结的剩余秒数建立新单调起点。用户手动暂停会清除自动恢复标记，因此系统唤醒不会误播放。

### 休息继续

休息开始时已经保存 `break_ends_at` 与 `force_ends_at` 两个墙钟 deadline。挂起和恢复都不会移动 deadline；恢复事件只让状态机观察新的墙钟，下一次快照直接得到正确剩余量和 `can_unlock`。

墙钟回拨使用“休息期间已经观察到的最大墙钟”钳制，倒计时不会反向增加。

## 自动测试

domain 测试使用构造时间，不会真的让机器睡眠：

- 工作 120 秒后挂起，睡眠 7,080 秒，唤醒时仍保留睡前剩余；
- 唤醒后再推进 60 秒，只扣这 60 秒；
- 手动暂停后经过 suspend/resume 仍不运行；
- 休息 60 秒后睡 300 秒，唤醒时休息和强制期都按墙钟推进；
- 墙钟回拨不增加休息剩余。

运行：

```bash
cargo test -p clock-domain -p clock-app
```

## 真机验收

自动测试不能代替 OS 电源通知实测。Windows 与 macOS 发布前分别执行以下用例，显示/触发允许约 ±1 秒。

### 1. 手动暂停后休眠

1. 工作运行一段时间后点“暂停”，记下剩余；
2. 系统睡眠 2 分钟；
3. 唤醒后仍为暂停，剩余与睡前一致。

### 2. 工作中休眠

1. 工作剩余约 3 分钟时触发系统睡眠；
2. 2 分钟后唤醒；
3. 剩余仍约 3 分钟，并自动继续倒计时。

外接屏对照：设置“合盖不操作”并继续在外屏使用，进程未挂起时工作倒计时应继续减少。

### 3. 休息中休眠

1. 设置休息 10 分钟、强制期 2 分钟；
2. 进入遮罩后系统睡眠 5 分钟；
3. 唤醒后休息约剩 5 分钟，强制期已结束，可完成算式提前解锁。

再测试睡眠超过 10 分钟：唤醒后显示“休息完成，可以解锁”，但遮罩不会自行消失。

### 4. 通知积压回归

1. 工作中立刻让系统睡眠，尽量不留一个完整 timer 周期；
2. 数分钟后唤醒；
3. 工作剩余不能一次扣掉整段睡眠时间。

该用例专门验证电源事件携带原始时间戳的实现。

## 已知边界

- 当前不持久化正在运行的阶段和 deadline；进程被杀后重新启动一轮工作，而不是恢复旧计时。
- 依赖操作系统正常发送 suspend/resume；极端驱动或电源策略下仍需从日志和平台事件排查。
