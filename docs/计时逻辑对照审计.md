# 计时逻辑对照审计

审计基线：Rust 合并节点 `ea1cc392b`（当前 `rust` 分支）与 `qwidget` 分支的 C++ 路径。需求基线见 [计时与休眠.md](./计时与休眠.md)：工作时真正系统休眠冻结，休息时按进入休息时记录的墙钟截止时间继续推进。

## 结论

Rust 当前 domain 实现与需求一致：

| 状态 | Rust 实际逻辑 | 需求 |
| --- | --- | --- |
| 工作中 suspend | 保存睡前剩余，停止工作单调时钟；resume 后从剩余继续 | 冻结 |
| 手动暂停 suspend | 不设置自动恢复标记，唤醒后仍暂停 | 冻结 |
| 休息中 suspend | `break_ends_at` / `force_ends_at` 不移动，唤醒快照按墙钟补算 | 继续 |
| 休息到点 | 遮罩保留，`can_unlock=true` 后由用户解锁 | 保留遮罩 |

Rust 代码对应 `crates/clock-domain/src/model.rs` 的 `suspend()`、`resume()`、`start_break()` 和 `snapshot()`；自动测试覆盖工作冻结、手动暂停不恢复、休息继续和墙钟回拨。

## QWidget 路径差异

`qwidget` 的文档把休息描述为按墙钟继续，但当前 C++ 实现仍有相反路径：

- `KtLockScreenManager::enter_system_sleep_at()` 调用 `breakClock_.freeze_for_system_sleep_at(...)`；
- `try_resume_after_wake()` 把 `forceEndMs_` 加上休眠时长；
- 这会使休息倒计时和强制期在休眠期间冻结，或因事件顺序产生不同结果。

因此，不能用 QWidget 的“已验证”表格证明 Rust 或 Windows 行为正确；Windows 休眠必须以 Rust domain 规则和真实 `WM_POWERBROADCAST` 验收为准。QWidget 路径若继续维护，应单独修正上述冻结/延期逻辑后再更新其验收状态。

## Windows 唤醒后误进入锁屏的排查点

Rust 每秒循环先消费电源事件，再处理 `Tick`；Windows 电源线程在 `WM_POWERBROADCAST` 回调中携带事件原始时间戳。若实机仍出现“睡眠期间工作倒计时减少，唤醒后立即锁屏”，应记录以下日志并确认顺序：

1. `Suspended` 是否在睡眠前进入主事件循环；
2. `Resumed` 是否在唤醒后进入主事件循环；
3. 两事件之间是否出现 `Tick`；
4. `Suspended` 事件的单调时间是否早于 `Resumed`，以及唤醒后工作剩余是否等于睡前快照。

如果 `Suspended` 没有收到，问题在 Windows 消息窗口/电源通知链；如果事件已收到但仍扣除睡眠时长，问题在单调时钟取值或事件消费顺序，而不是 Slint UI。

## 验收要求

- [ ] Windows 工作中睡眠 2 分钟，唤醒后剩余仍接近睡前值，并自动继续。
- [ ] Windows 休息中睡眠 5 分钟，唤醒后休息剩余减少约 5 分钟，强制期按墙钟判断。
- [ ] 睡眠期间不得因一次积压 `Tick` 直接触发 `StartBreak`。
- [ ] 记录 `Suspended`/`Resumed` 原始时间和状态快照；未完成 Windows 实机测试前，不标记为已验证。
